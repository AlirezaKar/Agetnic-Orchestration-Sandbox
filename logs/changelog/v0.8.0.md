# v0.8.0 — every step visible: LLM-written briefs, dependency waves, manager review, run log

- **Date:** 2026-10-31
- **State:** in review
- **Scope:** `app/orchestrator/` (planner, agents, executor, manager, new `trace.py`
  and `runlog.py`), `app/agent.py` (observer hook), `POST /orchestrate` payload,
  new `GET /runs` + `GET /runs/{run_id}`, `scripts.logs runs`, and the UI trace.

## Why

v0.7.0 built the manager, but two things were missing:

1. **The steps were invisible.** The UI showed a plan and a per-agent answer. It
   did not show the prompt an agent received, the tool calls it made, or what the
   manager did with the results — so the answer could not be audited.
2. **The plan was written by rules.** The requested design is: the manager
   delegates, the planner writes a plan for each selected agent (with the LLM),
   the agents work in parallel, and results that one agent needs reach the next
   one before the manager writes the final answer.

## What changed

### The pipeline, explicitly

```
1. classify   rules read the prompt, the files, the roster
2. plan       rules select the agents → the model writes each brief + dependencies
3. delegate   wave 1: independent agents in parallel
              wave 2: dependent agents receive the earlier agents' results as input
4. review     the manager reads the reports and may ask for one follow-up agent task
5. wrap up    the manager writes the answer (or a deterministic merge)
```

`ORCHESTRATOR_PLANNER` now means:

| Value | Selection | Briefs | Planner cost |
|---|---|---|---|
| `auto` (default) | rules | **the model** | 1 small call |
| `heuristic` | rules | rules | 0 calls |
| `llm` | the model | the model | 1 call |

The detail call is validated hard: one entry per selected agent, no unknown
agents, no self-dependency, no cycles (`_parse_detail_plan` + `_has_cycle`). If
anything is off, the rule-written briefs are used and the trace says so.

### Dependencies and waves

`PlanStep.depends_on → wave` is computed by `executor.schedule()`:

- independent agents share wave 1 and run with `asyncio.gather`
- an agent that depends on another runs later and receives its answer under
  *"Findings from agents that ran before you…"*
- a cycle, or a dependency on an agent that never ran, drops the step into the
  next wave instead of deadlocking

The heuristic planner already uses this: the generalist joins only when
reasoning is asked for, and then it **waits** for the specialists instead of
working beside them.

### Manager review

`ORCHESTRATOR_REVIEW=true` (default, "true" only when more than one agent ran):
one small completion decides whether a follow-up is needed. It may request up to
two `{agent, task}` items, validated against the roster, which are then run in a
new wave with the earlier results as input. Everything is traced, including the
common "no extra work needed" outcome.

### The trace

`app/orchestrator/trace.py` records ordered events
(`run · planner · agent · tool · manager · synthesis · merge · done`) with
`seq`, `offset_ms`, stage, actor and a detail dict. Recorded verbatim:

- the exact `messages` sent to the planner, to each agent and to the synthesis
- every tool call with its arguments, and every tool result
- each agent's reply, model/provider, usage and latency
- the deterministic computation behind the data agent
- the retrieved excerpts behind the document agent
- the follow-up request, if the manager made one

`WebSearchAgent` gained an optional `observer` callback, so the search loop's
prompts, tool calls and tool results land in the same trace without changing its
behaviour.

Long strings are clipped **only when serialised for the browser**
(`ORCHESTRATOR_TRACE_CHARS`, default 4000, with a "…N more chars" marker). The
stored record is unclipped.

### The run log

`logs/orchestrator/runs.jsonl` (one line per run) and
`logs/orchestrator/<run-id>.json` (pretty, full trace) — git-ignored, rotated
with `LOG_ROTATE_MB`. Read it with:

```bash
python -m scripts.logs runs                    # table of recent runs
python -m scripts.logs runs --run <id>         # every step with previews
python -m scripts.logs runs --run <id> --full  # full JSON details
curl -s localhost:8000/runs
```

### UI

Under every Auto answer, **How this answer was built**:

- header chips: agent chain, wave count, synthesis, agent ms vs total ms
- plan block: intent, who wrote the selection and the briefs, model calls, one
  line per step with its wave and its `← dependencies`
- the trace: one row per step, coloured by actor, each expandable into the
  prompt (role-labelled system/user/tool bubbles), tool arguments, tool results,
  computed figures, retrieved excerpts, replies and errors
- **Expand all steps** / **Collapse** / **Raw JSON**, plus the run id and the
  path of the stored record
- a sidebar **Run log** panel listing recent runs; clicking one loads the stored
  record into the inspector

Live check with a mock OpenAI-compatible provider (document + generalist):

```
plan  : document → general   briefs: llm   waves: [[document], [general]]
trace : 26 steps — planner prompt, 2 agent prompts, manager review, final synthesis
log   : logs/orchestrator/run-20261031-153930-fc0f41.json
```

The generalist's prompt contained the document analyst's finding, which is the
dependency behaviour in action.

## Known limits

- The trace makes the payload bigger: a four-agent run returns ~20–60 kB with
  the default clipping. Lower `ORCHESTRATOR_TRACE_CHARS` for smaller responses;
  the log file is unaffected.
- Clipping is per string, not global: a run with many long prompts can still be
  large. The UI renders it lazily (rows collapsed by default).
- Model "thinking" is only visible where the provider returns it as content; the
  trace shows the prompts and replies, not private chain-of-thought that an API
  does not expose.
- The review call adds one completion per multi-agent run; it is deliberately
  skipped for single-agent runs and can be disabled.
- The run log has no retention policy beyond rotation; delete the directory to
  start over.
