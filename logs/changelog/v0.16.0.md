## The problem

The harness could tell you what a run did — trace, run record, live thoughts —
and nothing about whether the *machine* was still sound. Every part of it can
regress silently: a planner that stops noticing attachments, a review loop that
runs twice, a record that loses a field, a stream that drops an event, a
dependency that stops waiting. Finding out meant writing an ad-hoc script, or
noticing a worse answer weeks later.

Two things made the honest version possible. The orchestrator talks to the world
only through four **ports** (`contracts.py`), so every external dependency can be
scripted — meaning the evaluation can be deterministic, keyless and fast instead
of a flaky benchmark of someone else's model. And the package owns its own
records, so the check can assert on the *artefacts* as well as the behaviour.

## What ships

**`app/orchestrator/audit.py`** — eighteen checks in eight levels, each a
function that returns `pass | warn | fail | skip` plus the metrics behind the
verdict and the findings it rests on:

| Level | Checks |
|---|---|
| `plan` | selection coverage on a golden set · model-written briefs and the fallback when the planner's JSON is broken · wave scheduling (independent, chain, cycle, dangling dependency) |
| `execute` | failure isolation · timeout fence · dependency ordering (later wave *and* later trace offset) |
| `gate` | the no-model evaluator's verdicts · evidence preservation (`keep_facts` refuses a rewrite that drops a URL) |
| `manager` | review gate (one agent → no review, capped rounds) · deterministic synthesis when there is no model |
| `record` | run record serialises with every promised field · the live stream delivers each event once, in order, and every event projects |
| `outcome` | grounding (no URL in the answer that the run did not find) · repeatability (five identical plans) |
| `robust` | 200 000-character file, empty prompt, invented agent name · instructions hidden in an attachment cannot re-plan the run |
| `live` | *(opt-in)* LLM planner vs the rules · stage latency of a real run — `skip` with the reason when no key is set |

The scripted world is small and lives beside the checks: `ScriptedModel` (answers
by role, can fail a role, can delay), `ScriptedSearch`, `ScriptedLoop` +
`ScriptedLoopFactory` (the search agent's port, including an answer, a failure
and a slow run). Attachments are built in memory, runs are written to a
temporary directory, and memory is never involved — an audit reads the code's
behaviour and leaves nothing behind.

**Four routes:**

```
GET  /audit          the catalogue + the last scorecard + what the host is wired to
POST /audit/run      run every check → the scorecard ({"live": true}, {"only": [...]})
GET  /audit/stream   the same run as SSE: open · start · check · result · error
GET  /audit/last     the newest scorecard on disk
```

`POST /audit/run` also writes `logs/audit/<audit_id>.json` (plus `latest.json`)
and `<audit_id>.md` — a table that diffs readably between versions. `logs/audit/`
is git-ignored: scorecards are run artefacts, not source.

**The button.** *Evaluate* sits in the top bar with a status pill beside it
(`Audit: not run` → `Audit: 16/18 pass`, tinted pass/warn/fail). The panel opens
as a **checklist, not a spinner**: all eighteen rows are listed with what each
proves, grouped by level, before anything runs. Pressing *Run audit* streams the
run and each row fills in as its verdict lands — a dot per state (queued,
spinning while running, then green/amber/red/grey), the one-sentence verdict, the
row's *metrics* disclosure with the numbers behind it, any findings, and the
elapsed milliseconds. A summary strip carries the counts, the total time, offline
vs live, the audit id and the file it saved. A **JSON** tab shows the same object
pretty-printed, with *Copy JSON* and *Download*.

Because the checks finish in ~300 ms, verdicts are revealed one at a time at
90 ms apiece and the final scorecard is held until the queue drains — the run is
fast, the *reading* is paced, and the JSON is the same object either way.

**The CLI**, for CI:

```bash
python -m scripts.audit                 # table, exit 1 on any failure
python -m scripts.audit --json          # scorecard on stdout
python -m scripts.audit --live          # also the two checks that call a model
python -m scripts.audit --only gate.rules,plan.waves
```

## What the audit found

It earned its keep before it shipped.

- **A 0.2 s timeout was reported as "timed out after 0s."** `executor.py`
  formatted the fence with `{timeout:.0f}`, so any sub-second
  `ORCHESTRATOR_TIMEOUT` told the user a lie. Now `{timeout:g}` → `0.2s`.
- **The `llm` planner cannot express a dependency.** `_parse_llm_plan` drops
  `depends_on`, and its prompt never asks for it — while the `auto` path's detail
  planner does both. `planner=llm` therefore always runs one flat wave. Left
  alone here (it is a planning-semantics change, not a fix), recorded as a known
  gap, and the dependency check exercises the `auto` path that actually ships by
  default.
- **My own golden set was wrong twice.** Two prompts selected more agents than I
  had written down, and both were right (a redundant generalist is harmless). The
  check now scores **coverage of the agents a request cannot be answered
  without** plus contradictions, not exact set equality — a heuristic that
  over-includes should not paint the audit red.

- `tests/test_audit.py` (22): the catalogue is ordered by level and every check
  explains itself; an offline run passes; a check that *raises* becomes a `fail`
  with the traceback as a finding; a `warn` makes the scorecard a `warn`; the
  audit writes **no** run records; the scorecard round-trips through JSON and

## Honest limits

- **The live checks are not run here**: no provider key in this workspace, so
  `live.planner` and `live.latency` report `skip` with the reason. Everything
  else is genuinely offline.
- **No browser in the sandbox** — the panel was verified in jsdom (both modes)
  and by hand against the running server's JSON, not by looking at a screenshot.
  The reveal pacing, the row states and the layout at small widths are covered by
  CSS and the jsdom assertions, not by a pixel check.
- **The audit judges the orchestration, not the models.** Grounding is checked
  against the run's own sources with a scripted answer; answer quality in the
  wild still needs the judge-based harness sketched earlier (blind pairwise,
  never self-graded), which is deliberately not part of this button.
