# v0.9.0 — harness memory: conversations you can reopen and continue

- **Date:** 2026-11-01
- **State:** merged — PR #14
- **Scope:** new `app/memory.py` (the store), new `scripts/memory.py` (the CLI),
  `POST /orchestrate` / `POST /chat` / `POST /search` (both now remember their
  turn and take a `session_id`), new `GET|POST /sessions` +
  `GET|PATCH|DELETE /sessions/{id}`, `app/main.py` (`_history_for`,
  `_remember`, `_remembered_error`), the UI Memory panel + chat replay,
  `MEMORY_*` settings, `.gitignore`, and `python -m scripts.doctor` (memory check).

## Why

The harness had an orchestrator, agents and tools — and no memory. Every answer
was written to `logs/orchestrator/` as a *trace*, which answers "what did the
machine do?", but nothing stored the conversation itself. Reload the page and
the chat was gone; there was no way to come back to yesterday's session and
keep going.

Memory is the missing part of the harness, and it is deliberately **not a log**:

| Base | Question it answers | Lifetime | Contains |
|---|---|---|---|
| `logs/` | what did the process do? | rotated | log lines, tracebacks, requests |
| `logs/orchestrator/` | what did the machine do in one run? | kept, one JSON per run | prompts, tool calls, timings, unclipped |
| **`memory/`** | **what did we say to each other?** | **kept until you forget it** | **every user turn, every answer, the payload the page rendered** |
| `.data/files/` | what was uploaded? | kept | attachment text + metadata |

## What changed

### The layout

```
memory/
  index.jsonl                 one line per session change (append-only index)
  sessions/<session-id>.json  the conversation: every turn, both sides
  sessions/<session-id>.md    the same conversation as readable markdown
```

A turn is stored as the pair the page showed:

```json
{
  "turn_id": "t-2",
  "at": "2026-11-01T09:14:03+00:00",
  "mode": "auto",
  "user":      {"text": "and the returns?", "files": [{"name": "policy.md"}]},
  "assistant": {"ok": true, "answer": "…", "provider": "groq", "model": "…",
                "run_id": "run-20261101-…", "agents": ["general"],
                "model_calls": 3, "trace_steps": 26,
                "response": { …the exact JSON the browser received… }}
}
```

`assistant.response` is the payload `POST /orchestrate` returned — so replay is a
re-render, not a regeneration: same bubble, same *How this answer was built*
panel, same trace steps, same sources. Nothing is re-asked from the model, so
reopening a session costs **zero** model calls.

### Why JSON and not SQLite

A conversation is a small self-contained document: greppable, diffable,
backup-able with `cp`, readable without the app. SQLite wins only past thousands
of sessions and would hide memory from every tool that already works on files.
The shape mirrors the run log (`index` for listing, one file per item for the
detail), so there is one mental model for both bases.

### Continuing a conversation

`POST /orchestrate`, `POST /chat` and `POST /search` accept:

| Field | Effect |
|---|---|
| `session_id` | continue that conversation; **created when unknown** and returned in `session` |
| `remember` | `false` keeps this exchange out of memory |

The response now carries `session: {session_id, turn_id, turns, title, path, stored}`.

Context comes from memory, not from the browser: when a `session_id` is known
and has turns, `_history_for()` builds the model history from the stored
conversation (`MEMORY_HISTORY_TURNS=6`) and **ignores the `history` array** the
page used to resend. A reloaded tab therefore continues with the real earlier
turns, and a browser that was never open for them still gets them. With no
session (or memory off) the old client-side `history` fallback still applies.

A failed turn is a turn too: configuration and provider errors are stored with
`ok: false` and the error body, so the transcript does not silently lose the
question you asked.

### API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/sessions?limit=&q=` | recent conversations (title, turns, modes, last message) |
| `POST` | `/sessions` | start an empty conversation (`{title, mode}`) |
| `GET` | `/sessions/{id}` | every turn with the payload to replay, plus a `resume` hint |
| `PATCH` | `/sessions/{id}` | rename (`{title}`) |
| `DELETE` | `/sessions/{id}` | forget it (file, markdown, index tombstone) |

`GET /health` and `GET /version` report the memory directory, session and turn
counts, and whether the directory is writable. Ids are sanitised to
`[A-Za-z0-9-_]` before they are ever used as a file name.

### The UI

- A **Memory** panel lists the conversations, newest first, with turn counts and
  relative time. Click one to reopen it: every turn is re-rendered exactly as it
  was, with the trace panel and all, and the next message continues it.
- The composer shows a session pill (`memory: 4 turn(s) · s-…`) so it is always
  clear which conversation you are in.
- **New chat** starts a fresh conversation; the previous one stays in memory.
  The delete button arms on first click (`delete?`), deletes on second.
- On boot the page reopens the last session you were in (stored in
  `localStorage`); if the backend has forgotten it, you simply start clean.

### CLI

```bash
python -m scripts.memory list
python -m scripts.memory show s-20261101-091403-a1b2c3
python -m scripts.memory search refund
python -m scripts.memory export s-… -o chat.md
python -m scripts.memory forget --all
```

`python -m scripts.doctor` gained a fifth section: the store path, session and
turn counts, and a probe round trip (write → reload → read) in a temp directory.

### Settings

| Variable | Default | Meaning |
|---|---|---|
| `HARNESS_MEMORY` | `true` | store conversations at all |
| `MEMORY_DIR` | `memory` | where they live (git-ignored) |
| `MEMORY_HISTORY_TURNS` | `6` | how many earlier turns the model gets back |
| `MEMORY_HISTORY_CHARS` | `3000` | clip per remembered message |
| `MEMORY_MAX_TURNS` | `200` | oldest turns dropped past this |

An unwritable directory never breaks a chat: the store degrades to in-process
memory, keeps working, and reports `writable: false` in `/health`.

## Verify

```bash
python3 -m unittest discover -s tests -t .          # 400 tests
python3 -m scripts.memory list                      # what is remembered
python3 -m scripts.memory show <session-id>         # both sides of every turn
python3 run.py --port 8000                          # then, in the browser:
```

1. Send a message in **Auto**; the composer pill shows `memory: 1 turn(s)`.
2. Reload the page — the conversation is back, trace panels included.
3. Send a follow-up: the trace's first event reports
   `history_turns: 2` even though the request carried no history.
4. **Memory** → another session → it opens; `+ New` starts a clean one.
5. `memory/sessions/<id>.json` (and `.md`) holds what you just saw.

## Known limits

- Memory is per machine and per `MEMORY_DIR`; there is no sync between instances.
- Attachments are remembered by name and id; the file body stays in
  `.data/files/`, so a deleted upload is a dead reference in an old transcript.
- The last restored session is tracked per browser (`localStorage`), not per user —
  there are no users in this harness yet.
- Client-side `history` is ignored whenever the memory has turns for the session;
  that is intentional (one source of truth) and is what `_history_for` documents.
