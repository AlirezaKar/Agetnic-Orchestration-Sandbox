# v0.11.0 — the run log can no longer 500 a request, and files ask permission

- **Date:** 2026-11-01
- **State:** merged — PR #18
- **Scope:** `app/orchestrator/runlog.py`, `manager.py`, `files.py`;
  `app/main.py` (`/favicon.ico`, `/files`, `/files/{id}/consent`,
  `/orchestrate`, `/health`, `/config`); `app/config.py`, `.env.example`;
  the composer UI (`index.html`, `app.js`, `extra.css`). No change to the
  planning algorithm, the agents, the trace format or the search/memory code.

## The two failures in the log

### 1. `POST /orchestrate` → 500 `TypeError: Object of type PlanStep is not JSON serializable`

The manager's review asks for a follow-up step and records it:

```python
info["steps"] = steps          # list[PlanStep] — live dataclasses
```

`Result.to_dict()` copied that dict straight into the record, and
`runlog.save_run()` called `json.dumps(record)` with no fallback and caught only
`OSError`. Any run in which the manager asked for extra work therefore finished
its work and then died while *writing the log* — the worst place to fail.

Fixed in three places, on purpose:

| Where | Change |
|---|---|
| `manager.Result.to_dict()` | `review` and `plan` go through `runlog.to_plain()` — dataclasses / anything with `to_dict()` become plain dicts before they reach a response |
| `runlog.to_plain()` | new helper: dicts, lists, tuples, sets, dataclasses, `to_dict()` objects, everything else → `str()` |
| `runlog.save_run()` | `json.dumps(..., default=_fallback)` and `except (OSError, TypeError, ValueError)` — logging can never fail a request again |

`GET /runs` and `logs/orchestrator/<run-id>.json` now contain the follow-up
steps as normal JSON objects (`agent`, `task`, `reason`, `inputs`,
`depends_on`, `wave`) instead of raising.

### 2. `GET /favicon.ico` → 500 `RuntimeError: Response content longer than Content-Length`

The route answered `JSONResponse(status_code=204, content=None)`; a 204 with a
`Content-Length` and a body line is a contradiction, and Starlette's error
middleware then sent a second response through the logging middleware, which is
where the double `http.response.body` came from.

* the route now returns `Response(status_code=204)` — no body, no length;
* `app/static/index.html` carries `<link rel="icon" href="data:,">` so the
  browser never asks for `/favicon.ico` in the first place.

`agetnic.doctor: model check failed`, `GET /admin → 404` and the `Ctrl-C`
`CancelledError`/`KeyboardInterrupt` traceback stay in the log: the first two are
real information, the third is uvicorn shutting down.

## File permission — the prompt you asked for

> "when a file could need my permission, show me a prompt I can accept or
> reject — and since this is a trusted workspace, allow it every time by default,
> with a `.env` switch."

One new setting, off by default:

```env
# show an allow / don't-allow prompt before an agent reads a file (off = allow)
FILES_PERMISSION_PROMPT=false
```

**Off (the default).** Uploads are allowed at once, exactly as before; no prompt,
no extra click. Nothing in the page changes.

**On.** The composer shows a prompt card under the attachments the moment a file
is added:

```
┌ Permission needed ─────────────────────────── Allow all · Don't allow any ┐
│ An agent may read an attached file only after you allow it — nothing is    │
│ uploaded until you answer.                                                 │
│ policy.md   4.2 KB · the agent cannot read it yet        [Allow] [Deny]    │
└────────────────────────────────────────────────────────────────────────────┘
```

* **Allow** — the file is uploaded with `consent: true` and the run proceeds.
* **Don't allow** — the file is dropped; nothing is read, nothing is sent.
* **Send** is blocked while a file is still undecided (the banner says which).

The API enforces the same rule, so a client cannot skip the prompt:

| Call | Meaning |
|---|---|
| `POST /files {…, consent: true}` | uploaded by a user who allowed it |
| `POST /files {…}` (no answer, flag on) | stored **pending**: `consent: false`, `needs_consent: true` |
| `POST /files/{id}/consent {"granted": true}` | the user allowed it |
| `POST /files/{id}/consent {"granted": false}` | the user refused — the file is deleted |
| `POST /orchestrate` with a pending file | **403** `consent_required` naming the files |
| `GET /files` | `pending` count + `consent` per file |
| `GET /health` | `files: {count, pending, permission_prompt, writable}` |
| `GET /config` | `files_permission_prompt` |

### The "problem relating to the permission" on upload

An upload could fail in two quiet ways, and neither said why:

* the store wrote the file, hit `PermissionError` (a `FILES_DIR` the process may
  not write) and swallowed it with `except OSError: pass`;
* the response was the plain summary, so nothing carried that fact back.

Now `AttachmentStore` remembers `writable` and the last error. The upload still
succeeds — the file stays in memory for the session — and the response says:

```json
{"id": "…", "stored": false,
 "warning": "the server could not write FILES_DIR, so this file is kept in memory for this session only (PermissionError: …)"}
```

The page shows that warning as a banner, and `/health.files.writable` reports the
same state up front. Consent lives in the sidecar next to the text, so it
survives a restart (`POST /files/{id}/consent` re-reads and writes it).
