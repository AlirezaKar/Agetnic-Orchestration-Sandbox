# v0.7.0 — Manager orchestration: planner → parallel agents → synthesis, plus file handling

- **Date:** 2026-10-31
- **State:** merged — PR #10, merge commit `a02e3fa`
- **Scope:** new `app/orchestrator/` package, `POST /orchestrate`, `POST/GET/DELETE
  /files`, `GET /agents`, Auto mode in the UI. The single-agent `/chat` loop is
  unchanged and still available.

## Why

The agent was only really good at web search: one model, one tool loop, and
every prompt went through the same path even when it needed nothing from the
web. A CSV in the prompt was just text; a PDF was impossible.

The manager fixes the shape of the problem:

```
user prompt ─► MANAGER ─► PLANNER ─┬─► document agent ┐
                                   ├─► web researcher ├─ parallel ─► MANAGER ─► one answer
                                   ├─► data analyst   │
                                   └─► generalist     ┘
```

The user also pointed out the cost trade-off: an LLM manager is more complete
but slower and more expensive. So the design is **adaptive, not LLM-first** —
see "What is and is not a model call" below.

## What changed

### `app/orchestrator/` — five small modules

| Module | Job |
| --- | --- |
| `planner.py` | reads the prompt + attachments, decides which agents run and what each must do. Heuristic rules by default, optional LLM planner |
| `agents.py` | the four specialists, same signature (`step, context → AgentOutcome`), plus keyword retrieval over attachments and table statistics |
| `executor.py` | `asyncio.gather` over the selected agents behind a `Semaphore(ORCHESTRATOR_MAX_PARALLEL)` and `asyncio.wait_for(ORCHESTRATOR_TIMEOUT)`; one agent failing never fails the run |
| `manager.py` | plan → execute → synthesis (or a deterministic merge), collects sources, errors, files, latencies |
| `files.py` | upload decoding, text extraction, and the on-disk attachment store |

### The four agents

| Agent | What it does | Needs |
| --- | --- | --- |
| **Document analyst** | retrieval over the attachments (keyword ranking over 1400-char chunks), then answers strictly from the excerpts, quoting the file | attachments (or it is skipped) |
| **Web researcher** | the existing `WebSearchAgent` tool loop — `web_search`, `fetch_url`, sources, trace | search chain |
| **Data analyst** | computes first (per-column sum/mean/median/min/max/stdev, blank counts, categorical top values, safe arithmetic on `12 + 30 + 45`) and only then narrates. Numbers are never invented by the model | nothing |
| **Generalist** | plain completion, no tools | model |

The generalist is **not** added to every plan: with specialists present it only
joins when the request also asks for reasoning ("explain", "compare", "why",
"design", …), because the manager already writes the final answer. One lookup
therefore costs one agent call plus one synthesis, not three calls.

### What is and is not a model call

| Stage | Default | `ORCHESTRATOR_PLANNER=llm` / `ORCHESTRATOR_SYNTHESIZE=false` |
| --- | --- | --- |
| plan | rules, ~0 ms, free | one small completion, falls back to the rules if the JSON is unusable |
| agents | 1 call each, in parallel | same |
| wrap-up | 1 completion | deterministic merge: each agent's answer, labelled |

No model at all still works: the document agent returns the retrieved extract,
the data agent returns the computed figures, and the manager merges them — with
an explicit note saying synthesis was skipped.

### Attachments

- `POST /files` takes `{"name", "data_b64"}` (what the page sends) or
  `{"name", "text"}`, and returns the parsed summary.
- Parsed without extra packages: text/`.md`/`.csv`/`.tsv`/`.json`/code,
  `.docx` (`word/document.xml`), `.xlsx` (`xl/worksheets` + `xl/sharedStrings`).
  `.pdf` needs `pip install pypdf`; without it the upload is rejected **415 with
  that instruction** instead of returning nothing. Legacy `.doc` gets a 415
  pointing at "save as .docx/.txt".
- Stored under `FILES_DIR` (`.data/files`, git-ignored) as text + a JSON sidecar,
  so an upload survives a restart; identical content is fingerprinted, and
  `GET /files` / `DELETE /files/{id}` manage the store.
- Limits: `FILES_MAX_MB` (default 10), `FILES_MAX_CHARS` (200 000, truncation is
  reported), `FILES_CONTEXT_CHARS` (12 000 per document prompt).

### API

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/orchestrate` | `{message, history, file_ids, agents?, planner?, synthesize?}` → answer + plan + per-agent results + sources + timings |
| `POST` | `/files` | upload one attachment, returns `{id, name, kind, chars, rows, columns, preview}` |
| `GET` | `/files` | what is in the store |
| `DELETE` | `/files/{id}` | drop one |
| `GET` | `/agents` | roster, planner mode, synthesis flag, readiness |

`/health` now reports `orchestrator` and the attachment count. All of it is also
under `/api/…`.

### UI

- **Auto (orchestrated)** is the first mode and the new default: the plan is
  rendered as a "Manager plan" panel with one collapsible card per agent —
  status, latency, model, why it was chosen, its answer, its sources.
- **📎 Attach** button and drag-and-drop anywhere on the page; chips show the
  name and size, removing one is a click. Files are uploaded only when a prompt
  is sent, and only in Auto mode.
- New **Orchestrator** sidebar panel: active roster, planner, synthesis,
  parallelism (from `/agents`).
- The run history and inspector record the full orchestration payload.

### `python -m scripts.doctor --orchestrate`

The doctor gained a fifth check: it runs the manager once and prints the plan,
each agent's status and latency, the wrap-up mode and the answer. It lands in
`artifacts/doctor.json` as `"orchestrator"`, with the same
`{"skipped": true, "reason": …}` shape when the flag is not given.


## Known limits

- Retrieval is keyword overlap, not embeddings: it is instant and dependency-free
  but will miss paraphrases. Long files are chunked (1400 chars, 150 overlap,
  first 400 chunks) and only the top 8 excerpts reach the model.
- `.pdf` needs the optional `pypdf`; scanned PDFs have no text layer either way.
- The heuristic planner is wording-based: an unusually phrased request can pick
  one agent too many or too few. `ORCHESTRATOR_PLANNER=llm` exists for that.
- The synthesis call sees the agent reports truncated to
  `ORCHESTRATOR_CONTEXT_CHARS`; very long specialist answers are cut mid-way by
  design rather than blowing up the context.
- Attachments are stored unencrypted on disk; the store is local-only and has no
  per-user separation.
