# v0.17.0 — the ARAS wiring: the orchestrator runs on the other app's microservices

- **Date:** 2026-11-08
- **Scope:** feature — a new `.env` block, a new client layer, two new orchestrator ports; the architecture is unchanged
- **State:** open — PR pending

## The problem

This orchestrator is being developed for an app whose capabilities already run
as microservices (the ARAS AI services: router, OCR, vector store, ingestion,
retrieval, data, web). Until now the sandbox only knew public third-party
providers — fine for testing the orchestration, wrong for the app it is meant
to live in. The access package documents one endpoint set and one token per
service; the sandbox had nowhere to put them and nothing that called them.

## What ships

**One `.env` block** (see `.env.example`): `ARAS_BASE_URL` (service ports are
appended automatically), per-service tokens falling back to a shared
`ARAS_TOKEN`, `ARAS_TENANT` + `ARAS_OWNER` for the data service's identity
headers, `ARAS_MODEL`, `ARAS_COLLECTION`, `ARAS_DATA_SOURCE_ID`, and
per-service URL overrides. **Nothing changes until a URL + token pair exists**
— with the block empty, every chain, agent and test behaves exactly as before.

**`app/aras.py`** — the only module that knows the services' URLs, auth and
JSON shapes: one thin client per service (OCR, ingestion, retrieval, vector,
web, data), the two port adapters, a `pdf_reader` factory and an async
`status()` used by `/aras` and `/diagnose`. Errors carry status + the
service's own `error`/`detail` text and a hint (tunnel? token inactive?) —
never the token itself.

**The wiring, through the seams that already existed:**

| Service | Becomes |
|---|---|
| router :8101 | LLM preset `aras` — OpenAI-compatible, **leads the auto chain** when configured; presets gained `trailing_slash` because Django 301-redirects a slashless POST and the body dies with it |
| web :8108 | search backend `aras` — **leads the search chain** when configured; 502/503 → `SearchError` → the chain falls through to ddg/wikipedia |
| ocr :8102 | `files.extract` gained an injectable `pdf_reader` port; uploads OCR PDFs through the service, local `pypdf` stays the fallback either way |
| retrieval :8105 | **new port `contracts.KnowledgeStore`** — no attachment + a wired store → the document agent retrieves from `ARAS_COLLECTION` and answers grounded in source filenames (RAG) instead of skipping |
| ingestion :8104 | `ARAS_AUTO_INGEST=true` indexes every accepted upload's text into the collection; failures are a warning on the upload response, never a failed upload |
| data :8107 | **new port `contracts.DataBackend`** — nothing local to compute + a wired backend → the data agent asks `POST /v1/query/` and reports answer, columns, rows and the SQL it ran |
| vector :8103 | health/diagnostics only, as the access README advises |

**Rules that keep it predictable:** local work stays first (attached tables
and plain arithmetic never leave the process; an attached file always beats
the knowledge store); a down service is an *outcome* (`failed` with the
reason), not a crash; the orchestrator package boundary holds — the ports live
in `contracts.py`, the clients host-side in `app/aras.py`, wired only in
`app/main.py`.

**Observability:** `GET /aras` reports endpoints, per-service health (each
service's unauthenticated `/health` probe — one call answers "is the tunnel
up"), RAG/data readiness and whether router/web actually lead their chains.
`GET /diagnose` carries the same block and three new hints; the Run
diagnostics panel renders one row per service.

## Honest limits

- This sandbox cannot reach the ARAS server (no tunnel, no tokens), so every
  integration is verified against mocked HTTP matching the shapes in the
  access README — the first run against the real services is the user's.
  `GET /aras` exists precisely to make that first contact a one-call check.
- `POST /v1/research/`, document download/delete on ingestion, few-shots and
  the vector store's point-level API are deliberately not wrapped: the
  orchestrator does not need them yet, and dead client code is a liability.
- The data agent uses one configured source (`ARAS_DATA_SOURCE_ID`); choosing
  between several registered sources per question is future work, noted in
  the module docstring.
