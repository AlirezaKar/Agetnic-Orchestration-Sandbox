# v0.16.1 — the audit audits itself: `live.planner` fixed, live path now in CI

- **Date:** 2026-11-08
- **Scope:** patch — one broken check, four new tests, no route or UI change
- **State:** open — PR pending

## The problem

The first `--live` audit run by a user (audit-20261107-132003-b92ad0, on a real
provider key) came back **17 pass / 1 fail**:

```
live.planner  fail  3 ms  the check itself raised:
              ValueError: too many values to unpack (expected 3, got 4)
```

The last change before 0.16.0 shipped rewrote `plan.selection` to score
*required-agent coverage* instead of exact set equality, which widened
`GOLDEN_PLAN` from 3-tuples to 4 — `(message, must, must_not, with_file)`.
`live.planner` still unpacked three. The engine contained the crash exactly as
designed (a raising check becomes a `fail` with the traceback as findings, the
other seventeen checks ran to completion), but the verdict was still a bug in
the audit, not in the orchestration being audited.

Why every gate missed it: the `live.*` checks skip without a provider key, and
CI has no key — so the one code path that *required* a key was the one code
path nothing ever executed.

## What ships

- **`app/orchestrator/audit.py` — `live.planner` rewritten.** It now unpacks
  the 4-tuple golden set and scores the model planner the same way
  `plan.selection` scores the rules: coverage of the agents a request cannot be
  answered without, contradictions (`must_not` agents picked anyway), and
  `fallbacks_to_rules` — replies the parser rejected, detected via
  `plan.detail_source`. Verdicts: `pass` at coverage ≥ 0.9 with ≤ 1
  contradiction, `warn` ≥ 0.7, `fail` below. One new honesty rule: **five
  fallbacks out of five is a `warn`** ("every model reply was unusable — the
  rules planned instead"), because in that case coverage measures the rules,
  not the model, and a green row would be a lie.
- **The live path runs offline in CI.** `tests/test_audit.py` gains
  `GoldenPlanner`, a scripted provider that answers the real planner prompt
  from the golden set, plus four tests: both live checks run keyless with no
  skip and no self-traceback (the regression test that would have caught this
  bug); a covering model passes with coverage 1.0; an unusable model warns
  with `fallbacks_to_rules == prompts`; a model that only ever picks `general`
  fails with findings.

## Tests

- `python3 -m pyflakes app/orchestrator/audit.py tests/test_audit.py` → clean.

## Honest limits

- This sandbox still has no provider key, so `live.planner` against a real
  model was verified only through the scripted provider; the arithmetic and
  the unpack are the same code path, but a real model's coverage number comes
  from the user's machine, not from CI.
- The thresholds (0.9 / 0.7, ≤ 1 contradiction) are first guesses in the sense
  of the practitioner rule the audit already follows: they are hypotheses to
  revisit once a few real scorecards exist, not laws.
