# v0.15.1 — the thought projection cannot break a run

- **Date:** 2026-11-04
- **State:** in review (this branch)
- **Scope:** `app/orchestrator/live.py` (the projection) and one guard in
  `app/main.py` (the stream). No change to the pipeline, the trace, the payload,
  the UI or the settings.

## The bug

`POST /orchestrate/stream` returned **500** in the middle of a real run:

```
File "app/main.py", line 887, in _stream_run
    yield _sse("thought", live_thought(event))
File "app/orchestrator/live.py", line 221, in _detail_out
    for call in detail["tool_calls"]
TypeError: 'int' object is not iterable
```

The run itself was fine — the web search had answered, the model had called its
tool, the report was written. What crashed was the *decoration*: the projection
into a "thought".

**Why:** the trace reuses the field name `tool_calls` with two shapes. On a model
step it is a **list of calls**; on the `agent finished` event it is a **plain
count** (`"tool_calls": 1`). `_detail_out` wrote `if detail.get("tool_calls")`
and then iterated — fine for `0` (falsy, and the reason the local runs never hit
it) and fatal for `1`. The same shape-blind assumption existed for `items`,
`gaps` and `issues` in `_kind_and_text`.

## The fix

1. **Every collection is checked, not trusted.** One helper, `_is_list()`, and
   the projection asks for the shape it needs (`_detail_out`, the verdict line,
   the rewrite line, the wave line). A count is a count; a single gap written as
   a string is still shown; a dict is not iterated.

2. **The stream can no longer be killed by a thought.** `_project()` in
   `app/main.py` wraps the call: if an event ever again carries a shape nobody
   predicted, the watcher gets `plain_thought(event)` — the actor, the offset and
   the title, no `detail` — and a warning with the traceback goes to
   `logs/error.log`. The run continues, its remaining events keep flowing, and
   the `result` frame still arrives. This is the counterpart of the `try/except`
   already around `trace.sink`: **a watcher must never be able to break a run,
   and neither must a renderer.**

3. **`plain_thought()`** lives next to `thought()` and is exported from
   `app.orchestrator`, so a host can use the same fallback.

`/_project` also fixed the earlier failure the same way: the projection used to
be the one unguarded thing between a healthy run and the browser.

## Regression tests

`tests/test_live.py`:

* `tool_calls` as a count (`0`, `1`, `3`) projects without raising and adds no
  tools chip — the exact live payload is in
  `tests/test_orchestrator_api.py::test_the_event_shape_that_broke_0_15_0_projects_cleanly`;
* `tool_calls` as a list still becomes the tools chip;
* nine odd shapes (`items` as int/str/dict, `agents` as int/dict, `tool_calls`
  as str/int/None, `gaps` as int) all produce a thought instead of an exception;
* a single gap written as text is still shown;
* `plain_thought()` never touches `detail` and keeps the title.

`tests/test_orchestrator_api.py`:

* a projection that raises on one event costs **one** thought, not the run: the
  stream still ends with `result` and the answer, and the failed thought arrives
  as the plain fallback (checked by counting the thoughts against the number of
  projections attempted);
* **the live scenario end to end** — a fake model that really calls
  `web_search`, so the agent finishes with `tool_calls: 1`: the stream reaches
  the answer, the tool call and the tool result are thoughts of their own, and
  the finished event carries `status: ok` with no tools chip.

**Honest limit:** the crash came from a live provider run (a model that actually
called `web_search`); the regression reproduces the *payload* the trace produced
rather than the provider call, because the sandbox has no key. The shape is
recorded verbatim in the test, so the bug cannot come back unnoticed.
