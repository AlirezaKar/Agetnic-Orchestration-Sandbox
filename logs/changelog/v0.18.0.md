# v0.18.0 — the navbar grows menus, the ARAS wiring gets a button, and the all-503 mystery gets a fix

- **Date:** 2026-10-31
- **Scope:** feature + fix — a navbar redesign (two dropdowns), an ARAS wiring panel with a proof run, copy buttons for every report window, and a proxy-bypass fix for loopback HTTP
- **State:** merged — PR #38, merge commit `e300851`

## The problem

Three things came back from the field at once.

1. **Every ARAS service answered HTTP 503** in the user's diagnostics — all
   seven, each in 557–1405 ms. That pattern is not a closed tunnel: a closed
   tunnel refuses the connection and the report says "network error". When
   *every* port answers an HTTP error, **something else is answering** —
   almost always a VPN/system HTTP proxy that httpx picks up from
   `HTTP_PROXY`/`HTTPS_PROXY` (httpx defaults to `trust_env=True`) and then
   routes even `127.0.0.1` through. The user runs behind exactly such a VPN.
2. **The navbar had outgrown itself**: four status pills and three buttons in
   one row, with an ARAS wiring check (`GET /aras`) that only existed as a
   curl command.
3. **Reports were awkward to share**: the diagnostics rows, the providers
   list and the wiring report had no one-click way out of the page.

(The `live.py` `TypeError: 'int' object is not iterable` in the same error
log is from a pre-0.17.0 copy — the guard and its regression test shipped in
0.17.0; `git pull` is the fix, no code change here.)

## What ships

**The proxy fix** — `trust_env_for(url)` in `app/config.py`: loopback hosts
(`127.0.0.1`, `localhost`, `::1`, `0.0.0.0`) never honour the proxy
environment; public hosts still do (the VPN stays useful for geo-blocked
providers). Applied in all three HTTP client factories: `ArasClient._client`
and the OCR `pdf_reader` in `app/aras.py`, and `OpenAICompatProvider._client`
in `app/llm/openai_compat.py` (which also covers Ollama / LM Studio).

**Sharper failure text** — a failed ARAS health probe now carries the first
160 characters of the response body, so a proxy's error page is
distinguishable from a broken Django service at a glance. `/diagnose` gained
a dedicated hint: when every ARAS failure is an HTTP *response* (not a
connection error), it says so — "something is replying, the tunnel is not
closed" — and names `HTTP_PROXY`/`NO_PROXY` and the curl command to compare
with. And `aras.status()` no longer omits `router` from the `skipped` list.

**The navbar, reorganised** — the pill row and button row collapse into two
dropdowns:

- **Status ▾** — the LLM / SEARCH / Diag / Audit pills as rows, plus a new
  **ARAS** pill; the button itself carries one aggregate dot (red beats amber
  beats green).
- **Tools ▾** — Providers, **ARAS wiring** (new), Run diagnostics, Evaluate.
  Every element keeps its id (`btn-providers`, `btn-diag-top`,
  `btn-audit-top`, `pill-*`), so nothing else on the page moved.

**The ARAS wiring panel** — the "is it actually used?" test as a button:

- *Level 1, wiring:* does router :8101 lead the model chain, web :8108 the
  search chain, is RAG/data ready — straight from `GET /aras`.
- *Level 2, health:* one row per configured service with latency or the
  error (body snippet included), plus the proxy warning when every row is an
  HTTP error.
- *Level 3, proof:* a **Proof run** button fires one minimal
  `POST /orchestrate` and renders the run record's `provider` · `model` per
  agent — `aras · rayen-gemma4-31b` is proof positive; anything else names
  the fallback that answered instead.

**Copy buttons everywhere a report lives** — the diagnostics rows ("Copy
report JSON" → the full `/diagnose` payload), the providers modal, and the
ARAS panel (report + proof). The audit modal already had its own.

## Honest limits

- The proxy fix covers what httpx controls (`trust_env`). A TUN-mode VPN that
  captures loopback at the network layer is outside any process's reach —
  the new hint and the body snippet exist precisely to make that case
  visible, and the curl comparison settles it in one command.
- The proof run spends one real model call; it is a button, never automatic.
- This sandbox still cannot reach ARAS, so the panel was verified against
  the mocked shapes and the live `GET /aras` of an unconfigured stack; the
  first configured run remains the user's.
